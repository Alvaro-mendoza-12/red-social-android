## A. Arquitectura y antecedentes

```text
Android / Web ── HTTPS ── ingreso Ubuntu / Nginx ── API ── PostgreSQL
                                              ├── Realtime ── WebSocket
                                              └── Signaling ── Socket.IO
API ── eventos internos ── Realtime ── Redis Streams ── otras réplicas
API ── archivos / tareas de medios / notificaciones
Signaling ── coordinación Redis ── otras réplicas
Pares WebRTC ── medios directos o TURN según conectividad
```

La API conserva identidad, autorización, mensajes y catálogo en PostgreSQL. Redis distribuye eventos, participa en la rehidratación de directos y permite el conteo distribuido de peticiones. La caída del contador Redis deriva a PostgreSQL. En ese momento ambos trabajos compiten por el mismo pool. Los clientes y el importador aún consumen contratos con nombres históricos. Se conservaron sus rutas.

La separación de API, distribución de eventos y negociación RTC tiene una justificación observable. Al interrumpir un proceso de Signaling se recuperó el directo en otro. La prueba no justifica extraer más microservicios ni añadir réplicas de escritura. Persisten dependencias compartidas del primario PostgreSQL, el volumen de objetos, el ingreso y la instancia Redis del Compose.

Se contrastaron los [ciclos 219](219-certificacion-tecnica-breakpoint-caos-seguridad-fuzzing-2026-11-19.md), [220](220-certificacion-escalabilidad-multiinstancia-soak-cobertura-2026-11-19.md) y [221–223](221-223-fortalecimiento-seguridad-rehidratacion-live-rendimiento-soak-release-2026-11-20.md) con sus arneses. En 221, 1.500 significa trabajadores lógicos reutilizando 24 identidades. Sus 3.000 operaciones a 452,3 req/s duraron aproximadamente 6,6 s. El ensayo de caída desconecta 30 sockets y conserva otros 30. El escenario original de bloqueo dormía y liberaba la conexión antes de generar tráfico. Las cifras históricas se mantienen asociadas a sus condiciones.
